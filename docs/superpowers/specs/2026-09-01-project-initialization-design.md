# CUMCM 项目初始化设计

## 1. 背景与目标

本仓库用于全国大学生数学建模竞赛的团队协作。目前仓库只有简略的 `README.md` 和空的 `AGENTS.md`，工具链尚未确定。

本次初始化的目标是建立一套最小、稳定、可扩展的协作结构，使团队能够：

- 保持官方输入不被污染；
- 并行探索多个模型，同时明确哪些代码能支撑论文；
- 让论文中的图、表和关键数字可以追溯并重新生成；
- 只维护一份权威论文源稿；
- 将工作区与最终提交物隔离；
- 记录重大决策和 AI 工具使用情况；
- 在尚未决定 Python、MATLAB、LaTeX 或 Word 时避免过早绑定工具链。

## 2. 设计原则

目录只在文件的来源、可修改性、生成方式或交付方式不同的时候建立。项目按照以下单向生命周期组织：

```text
外部输入 → 探索试验 → 正式代码 → 可再生产物 → 论文 → 冻结提交物
```

协作优先级为：

1. 官方输入不被污染；
2. 结果正确且可复现；
3. 论文与代码、产物一致；
4. 协作过程不覆盖他人工作；
5. 在满足上述条件后追求速度和排版效果。

## 3. 目录结构

```text
CUMCM/
├─ AGENTS.md
├─ README.md
├─ DECISIONS.md
├─ AI_USAGE.md
├─ .gitignore
├─ .gitattributes
├─ inputs/
│  ├─ official/
│  └─ external/
├─ experiments/
├─ src/
├─ outputs/
├─ paper/
├─ submission/
└─ docs/
   └─ superpowers/specs/
```

各路径职责如下：

| 路径 | 职责 | 关键约束 |
|---|---|---|
| `inputs/official/` | 赛题、官方附件、官方数据和官方模板 | 只读；不得覆盖、重命名或清洗原件 |
| `inputs/external/` | 团队自行收集并在建模中实际使用的数据 | 记录来源；纳入支撑材料清单 |
| `experiments/` | 候选模型、探索脚本、Notebook 和一次性试验 | 不直接作为论文正式结果来源 |
| `src/` | 已整理、已验证、可复现的正式代码 | 使用仓库相对路径；结果写入 `outputs/` |
| `outputs/` | 由代码生成的图、表、数值结果和必要日志 | 不手工修改；正式产物可纳入 Git |
| `paper/` | 唯一权威论文源稿、模板和引用文件 | Word 与 LaTeX 不双轨维护 |
| `submission/` | 从冻结提交生成的最终论文和支撑材料 | 不在此目录直接编辑 |
| `docs/superpowers/specs/` | 已确认的项目设计说明 | 仅保存长期有效的设计依据 |

空目录通过 `.gitkeep` 纳入 Git。暂不预建 `data/raw/interim/processed/`、`notebooks/`、`references/`、`tests/`、`configs/`、`scripts/` 或按工具、成员划分的目录；真实需求出现时再增加。

## 4. 根文件职责

### `README.md`

作为团队入口，使用中文说明：

- 项目目标与当前阶段；
- 目录地图；
- 从输入到提交的工作流；
- 当前工具链和论文格式的决策状态；
- 分支、任务认领和二进制文件协作方式；
- 结果晋升与交付的完成标准。

工具链未确定时明确标记为“待决定”，不编造安装、运行或测试命令。

### `AGENTS.md`

作为适用于整个仓库的稳定执行契约，采用简短、命令式规则，覆盖：

- 中文文档、UTF-8 和仓库相对路径；
- 目录不变量和唯一事实源；
- 数据与计算结果的可追溯性；
- 随机种子、参数、单位和边界条件检查；
- 科研诚信、文献来源和 AI 输出人工核验；
- 保留他人改动、禁止破坏性 Git 操作；
- Word、Excel 等二进制主文件的单一编辑者规则；
- 验证、交付说明和敏感信息保护；
- 新增顶级目录的条件。

`AGENTS.md` 不保存成员姓名、当天分工、临时进度或不存在的工具命令，也不复制完整项目介绍。

### `DECISIONS.md`

记录会长期影响结果或协作方式的重大选择。每条决策包含日期、状态、背景、决定、理由、备选方案和影响范围。工具链、论文格式、数据口径、核心模型、评价指标或重要假设改变时更新。

### `AI_USAGE.md`

作为 AI 使用详情的可编辑源记录。每条记录包含日期、阶段、工具与型号、用途、主要提示方式、采纳内容、人工修改、核验方法和相关文件。竞赛期间若实际使用 AI，可据此生成支撑材料所需的 `AI工具使用详情.pdf`；未使用时保留明确的未使用声明。

### `.gitignore` 与 `.gitattributes`

`.gitignore` 排除操作系统文件、编辑器配置、密钥、本地环境、缓存、临时 Office 文件、运行日志和可随时重建的临时产物，但不整体忽略 `outputs/`，以便共享论文实际采用的正式图表和结果。

`.gitattributes` 统一文本文件处理，并将 Word、Excel、PDF、压缩包和常见图片标记为二进制，减少无意义差异和错误合并。

## 5. 协作工作流

采用轻量的主干开发方式：

1. 从最新 `main` 创建短生命周期分支；
2. 通过任务或群内约定明确负责人和修改范围；
3. 按问题或模型命名工作，不按成员建立私人目录；
4. 使用小而完整的提交，高频同步和合并；
5. 合并前由另一名成员检查关键公式、数据口径和结果一致性；
6. 保持 `main` 中正式代码可运行、正式论文源唯一；
7. 禁止强推共享分支或改写共享历史。

探索成果的晋升流程为：

```text
experiments 中试验
  → 确认模型和口径
  → 整理到 src
  → 运行并生成 outputs
  → 人工核验
  → 引入 paper
```

若论文使用 Word 或其他难以合并的二进制格式，同一时段指定一名整合者，其他成员通过文本片段、批注或明确的修改清单提交内容。

## 6. 提交与合规

`submission/` 是发布区，而不是另一套工作副本。最终提交应从一个明确的冻结 Git 提交生成，原则上只保留最终论文和支撑材料压缩包，并完成以下检查：

- 论文与支撑材料内容一致；
- 正式源码完整且可以运行；
- 外部数据及必要中间结果已列入支撑材料；
- 论文附录中的文件清单与压缩包一致；
- 文件不包含参赛者、学校、赛区等不应出现的身份信息；
- AI 使用声明及详情与实际使用情况一致；
- 文件名、格式和大小符合当年官方规则。

当年规则属于时效信息，提交前必须重新核对竞赛官网，不能只依赖本设计文档。

## 7. 验证标准

初始化完成后执行以下验证：

1. 检查所有约定目录和根文件存在；
2. 检查文档均为中文、UTF-8，且不存在占位符或矛盾规则；
3. 检查 `.gitignore` 能排除典型缓存、密钥和 Office 临时文件；
4. 检查 `outputs/` 中的正式产物不会被整体忽略；
5. 检查 Git 只包含本次初始化预期的文件；
6. 检查 README、AGENTS、决策模板和 AI 使用模板的职责互不重复。

## 8. 非目标

本次初始化不做以下工作：

- 不决定 Python、MATLAB、LaTeX 或 Word；
- 不安装依赖或创建语言环境；
- 不提供尚不存在的运行和测试命令；
- 不建立 CI、自动打包或论文构建流程；
- 不写入具体赛题、成员名单、分工或模型结论；
- 不创建备份、归档或多个“最终版”目录。
