# 问题1：三种定位区域算法的效率对比

整理日期：2026-09-11。状态：探索性算法比较已完成；不是官方模拟器测试，团队人工复核待完成。

## 1. 结论

若一次性给出全部测向结果、只需要最终定位区域，继续采用当前方法 A：极角排序＋双端队列。它具有 O(m log m) 最坏情况保证，在本机对全部已测规模也最快。

“全部直线两两求交再排除”（方法 B）只适合作为小规模独立核验器。它最多产生 Θ(m²) 个候选交点；逐个检查全部约束的最坏时间为 O(m³)，输入顺序还会显著影响提前排除的效率。

“每次加入约束就裁剪当前多边形”（方法 C）最适合在线过程：已有 k 条边时，加入一个半平面的简单更新为 O(k)，一次测向对应连续裁剪两次。若从零批量处理全部约束，其总时间是 O(Σk_i)，最坏 O(m²)；只有中间多边形长期保持很少边时，才可能比方法 A 的排序更划算。

因此，本次比较不改变 `DECISIONS.md` 的 D-004：第一问批量算法保留 A。后续第三、四问若需要每次测量后立即决策，则应复用 C 的增量更新思想，而不是每次从头重跑 A。

## 2. 对比口径

一次测向产生两条半平面。下文用 m 表示半平面数量，因此检测点数 n=m/2；h 表示最终定位多边形边数，k_i 表示第 i 次裁剪前的中间多边形边数。

三种方法均输入同一组 `HalfPlane`，使用当前代码相同的整数归一化和 `Fraction` 精确谓词，并在区域生成后调用同一个旋转卡壳函数求直径。计时包括“构造最终区域＋求直径”，不包括生成输入和写 JSON。

| 方法 | 区域构造方式 | 批量时间 | 额外空间 | 适合回答的问题 |
|---|---|---:|---:|---|
| A：排序队列 | 按边界方向排序，只维护可能成为最终边界的约束 | O(m log m)，已排序时 O(m) | O(m) | 全部输入已知，只求最终区域 |
| B：全交点排除 | 枚举所有直线对，每个交点再检查约束 | 最坏 O(m³)，仅生成交点已需 Θ(m²) | 字面保存全部交点为 O(m²)；本实现流式去重 | 教学、很小规模的独立对照 |
| C：逐次裁剪 | 用第 i 个半平面扫描并裁剪当前 k_i 边多边形 | O(Σk_i)，最坏 O(m²) | O(max k_i) | 每加入新观测就需要更新和决策 |

方法 B 若遇到违反约束就提前停止，实际检查量可能小于 m³，但最坏界不变。方法 C 的“区域越来越小”也不等于边数越来越少；连续切角可以使 k_i 随 i 增长。

若每一步都需要输出 P_1,…,P_m，方法 C 的总复杂度恰好随这些中间边界的总规模增长。反之，若只需要 P_m，方法 A 无需为中间区域付费，最坏情况更稳妥。

## 3. 可复现实测设计

运行环境记录在 `outputs/q1/algorithm_comparison.json`：Python 3.13.13，Windows 11，Intel64 Family 6 Model 198 Stepping 2。使用 `time.perf_counter_ns`；m<96 重复5次，m≥96重复3次，表中取中位数。

测试 m∈{8,16,32,64,96,128}，共3类输入、54个“场景－规模－方法”组合：

1. **全部有效、按边界顺序到达**：最终 h=m；中间多边形边数持续增长。
2. **全部有效、固定种子打乱顺序**：最终仍为同一个 h=m 多边形，用于观察输入顺序影响。
3. **绝大多数冗余**：前4条约束形成正方形，其余均不改变区域，始终 h=k_i=4；这是对方法 C 有利的输入。

每个组合中，方法 B、C 的精确顶点集合和精确直径平方必须与方法 A 完全一致，否则脚本立即失败。本轮54个组合全部一致。

## 4. 计时结果

以下单位为毫秒，只摘录 m=16、64、128；完整18组规模结果和操作计数保存在 JSON 中。单次计时很短，绝对值会随机器负载变化；主要看随 m 增长的趋势和数量级。

| 场景 | m（n） | h | A 排序队列 | B 全交点排除 | C 逐次裁剪 |
|---|---:|---:|---:|---:|---:|
| 全部有效、有序 | 16（8） | 16 | 0.559 | 2.565 | 1.567 |
|  | 64（32） | 64 | 1.976 | 118.854 | 18.239 |
|  | 128（64） | 128 | 4.018 | 899.903 | 67.197 |
| 全部有效、打乱 | 16（8） | 16 | 0.500 | 2.550 | 1.486 |
|  | 64（32） | 64 | 1.893 | 42.008 | 18.002 |
|  | 128（64） | 128 | 3.917 | 203.736 | 68.592 |
| 大部分冗余 | 16（8） | 4 | 0.283 | 1.012 | 0.663 |
|  | 64（32） | 4 | 0.782 | 11.438 | 2.046 |
|  | 128（64） | 4 | 1.645 | 43.981 | 4.197 |

在 m=128 时：

- 全部有效、有序：B 为 A 的约224倍，C 为约16.7倍；
- 全部有效、打乱：B 为 A 的约52倍，C 为约17.5倍；
- 大部分冗余：B 为 A 的约26.7倍，C 为约2.6倍。

当前精确实现中，A 在8至128条半平面的所有场景均最快。不能把这解释为“C 永远不可能更快”：本次 A 的实现常数较小，而 C 逐边复制 `Fraction` 顶点；不同语言、数据结构和浮点实现会改变常数。

## 5. 操作计数解释

m=128 时，算法内部计数如下：

| 场景 | A 求交次数 | B 直线对 | B 半平面可行性检查 | C 边扫描次数 | C 峰值边数 |
|---|---:|---:|---:|---:|---:|
| 全部有效、有序 | 394 | 8128 | 363679 | 8386 | 128 |
| 全部有效、打乱 | 394 | 8128 | 77724 | 8223 | 128 |
| 大部分冗余 | 328 | 8128 | 13809 | 512 | 4 |

A 的求交次数保持线性；B 无论结果简单与否都必须访问8128个直线对。B 的有序输入反而更慢，是因为交点在约束列表中更晚才被判出不合法，提前退出较少。这说明 B 不仅渐近复杂度差，实际运行也对约束排列敏感。

C 在冗余场景只扫描4×128=512条边，符合 O(m·平均边数)；在全部有效场景累计扫描约 m²/2 条边，与平方增长一致。输入打乱没有从根本上改变最终每条边都有效这一事实，因此改善有限。

## 6. 怎样选择

### 第一问：全部观测已给出

采用 A。题面要求“已知若干检测点及示向度，给出计算定位区域直径的算法”，并没有要求逐次展示每个中间区域。A 给出最强的通用最坏界，当前实现也已有自动验证。

### 后续问：每次测量后必须立刻选下一动作

采用 C 保存当前区域。若当前有 k 条有效边，一次新测向产生两个半平面，简单更新代价约为两次 O(k) 扫描。相比之下，把全部历史约束重新交给 A，需要 O(m log m)；若每一步都这样重算，总计 O(m²log m)。C 总计 O(Σk_i)，最坏 O(m²)，且同时得到决策真正需要的每一步区域。

这里比较的是“C 增量更新”与“当前 A 从头重算”。若未来实现动态半平面交数据结构，结论需重新评估；当前仓库没有该实现。

### 方法 B 的合理用途

保留为测试 oracle，不进入正式求解路径。对于本题常见的少量检测点，B 的绝对时间可能仍只有毫秒级，所以很适合检查 A、C 是否输出同一顶点和直径；但没有理由让正式算法承担其平方数量候选点和立方最坏检查量。

不存在只由 m 决定的普适切换阈值。批量时可用

\[
T_A\approx a m\log m,
\qquad
T_C\approx c\sum_i k_i=c m\bar{k}
\]

判断：当平均中间边数 \(\bar{k}\) 长期显著小于 \((a/c)\log m\) 时，C 才可能在批量计算中领先；系数 a/c 必须由最终语言和数据结构实测。本轮即使 \(\bar{k}=4\)，C 到 m=128 仍未超过 A，说明不能只凭复杂度写死数值阈值。
